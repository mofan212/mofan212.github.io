1. 自动配置

1.1 自动配置 MVC 过滤器

CharacterEncodingFilter 是 Spring 提供的 Servlet 过滤器，用来设置 HTTP 请求和响应的字符编码，可以用于处理因编码不一致造成的中文乱码问题。

使用 Spring Boot 时，无需手动声明这个过滤器，而是根据条件自动注册它。

那它是怎么来的呢？

先说答案：Spring Boot 通过 HttpEncodingAutoConfiguration 向 Spring 容器注册了这个过滤器。

怎么测试一下呢？

使用 WebApplicationContextRunner 单独加载这份配置，看看容器里有什么：

12345678910111213141516171819public class HttpEncodingAutoConfigurationTest implements WithAssertions {
    /**
     * 复用加载 HTTP 编码自动配置的基础设置
     * 每次调用 run() 都创建新的容器，并在回调结束后关闭
     */
    private final WebApplicationContextRunner contextRunner = new WebApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(HttpEncodingAutoConfiguration.class));

    /**
     * 未配置编码属性时，自动配置提供默认的 UTF-8 过滤器
     */
    @Test
    public void testDefaultEncodingCreatesUtf8Filter() {
        this.contextRunner.run(context -> {
            assertThat(context).hasSingleBean(CharacterEncodingFilter.class);
            assertThat(context.getBean(CharacterEncodingFilter.class).getEncoding()).isEqualTo("UTF-8");
        });
    }
}

简单说下 WebApplicationContextRunner 的作用：

  • 它是 Spring Boot 提供的测试工具，可以用来创建带有 Servlet 环境的 Spring 容器。

在上述测试类中，创建 WebApplicationContextRunner 对象后，调用 withConfiguration() 方法添加 HttpEncodingAutoConfiguration 相关的配置。

注意，此时还没有创建 Spring 容器。

调用 run() 方法后，Runner 才会创建并启动容器，其中的 context 就是创建的 Spring 容器。回调结束后，Runner 又会自动关闭容器。

使用 WebApplicationContextRunner 提供的模拟 Servlet 环境，不需要启动 Tomcat，并且 Spring 容器用后即毁，非常好用！

如果要额外修改属性或添加用户配置，还可以调用 withPropertyValues() 和 withUserConfiguration()。它们会返回新的 Runner，不会影响原来的 contextRunner。

尝试自定义一个 CharacterEncodingFilter 过滤器：

1234567891011121314151617181920/**
 * 用户声明同类型过滤器后，自动配置不再注册默认过滤器
 */
@Test
public void testUserFilterMakesDefaultFilterBackOff() {
    this.contextRunner.withUserConfiguration(UserFilterConfiguration.class).run(context -> {
        assertThat(context).hasSingleBean(CharacterEncodingFilter.class)
                .doesNotHaveBean("characterEncodingFilter");
        assertThat(context.getBean(CharacterEncodingFilter.class))
                .isSameAs(context.getBean("customCharacterEncodingFilter"));
    });
}

@TestConfiguration(proxyBeanMethods = false)
static class UserFilterConfiguration {
    @Bean
    CharacterEncodingFilter customCharacterEncodingFilter() {
        return new CharacterEncodingFilter();
    }
}

此时默认过滤器不再注册，取而代之的是用户自定义的过滤器。

@TestConfiguration 是专门用于标记测试用的配置类，避免其他测试在扫描常规组件时把它扫进去，是专门用于测试的定制版 @Configuration。

那么问题来了：

  1. 默认过滤器是怎么注册进 Spring 容器的？
  2. 为什么自定义过滤器后，默认的过滤器就不注册到 Spring 容器了呢？

1.2 @SpringBootApplication

主启动类上的 @SpringBootApplication 组合了三个注解：

123456789@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = {
        @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class)
})
public @interface SpringBootApplication {
    // --snip--
}

它们的作用是：

  • @SpringBootConfiguration 组合了 @Configuration，用于声明 Spring Boot 配置类
  • @EnableAutoConfiguration 通过 ImportSelector 查找自动配置类
  • @ComponentScan 用于扫描应用中的组件，默认扫描范围是被标记的类所在包及其子包

其中：

  • @ComponentScan 用于扫描项目应用内的组件
  • @EnableAutoConfiguration 则用于导入三方 JAR 中的自动配置类

主启动类的 main() 方法里调用 SpringApplication.run() 时，启动类作为 Spring 容器中的第一个配置类，后续 Spring 依次解析这些注解完成组件的添加。

1.3 @EnableAutoConfiguration

重点看 @SpringBootApplication 里的 @EnableAutoConfiguration：

12345@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {
    // --snip--
}

它也是一系列注解的集合。

先看 @AutoConfigurationPackage：

1234@Import(AutoConfigurationPackages.Registrar.class)
public @interface AutoConfigurationPackage {
    // --snip--
}

通过 @Import 导入 AutoConfigurationPackages.Registrar，默认把主启动类所在的包名登记到容器中：

12345@Override
public void registerBeanDefinitions(AnnotationMetadata metadata, BeanDefinitionRegistry registry) {
    // metadata 是主启动类的元数据，包含包名、注解等信息
    register(registry, new PackageImports(metadata).getPackageNames().toArray(new String[0]));
}

注意，执行 register() 方法只登记包名，不会执行组件扫描。

再看 @Import 导入的 AutoConfigurationImportSelector。

1234public class AutoConfigurationImportSelector implements DeferredImportSelector, BeanClassLoaderAware,
        ResourceLoaderAware, BeanFactoryAware, EnvironmentAware, Ordered {
    // --snip--
}

它实现了 DeferredImportSelector。Deferred 是推迟的意思，要知道它推迟了什么，得回到 Spring 解析 @Import 的地方。

Spring Boot 主启动类也是一个配置类，它同样会经过 Spring 配置类的解析 中讲过的解析过程。如果从启动入口开始，那么会经过下面这些调用：

1234567SpringApplication.run()
  └─ 刷新 ApplicationContext
      └─ invokeBeanFactoryPostProcessors()
          └─ ConfigurationClassPostProcessor
              └─ processConfigBeanDefinitions()
                  └─ ConfigurationClassParser.parse()
                      └─ processImports() 处理 @Import

ConfigurationClassParser#processImports() 处理 ImportSelector 时，会判断它是否实现了 DeferredImportSelector。

这里的 selector 就是前面的 AutoConfigurationImportSelector 实例：

12345678if (selector instanceof DeferredImportSelector deferredImportSelector) {
    this.deferredImportSelectorHandler.handle(configClass, deferredImportSelector);
}
else {
    String[] importClassNames = selector.selectImports(currentSourceClass.getMetadata());
    Collection<SourceClass> importSourceClasses = asSourceClasses(importClassNames, filter);
    processImports(configClass, currentSourceClass, importSourceClasses, filter, false);
}

AutoConfigurationImportSelector 实现了 DeferredImportSelector，因此会进入 if 分支，把这个实例交给 deferredImportSelectorHandler 保存。

等本轮配置类遍历结束，parse() 再调用 deferredImportSelectorHandler.process()，统一处理之前保存的 DeferredImportSelector 实例：

12345public void parse(Set<BeanDefinitionHolder> configCandidates) {
    // 遍历并解析本轮配置类
    // --snip--
    this.deferredImportSelectorHandler.process();
}

因此 Spring Boot 中，是先选好要导入哪些自动配置，然后再逐个解析。

选择和解析都是在本轮 parse() 方法返回前处理，此时 Spring 容器里还没有那些在配置类里声明的 Bean。

1.4 延迟分组导入

Spring 处理 DeferredImportSelector 时，会调用 getImportGroup() 获取分组类型。

AutoConfigurationImportSelector 返回 AutoConfigurationGroup.class，由这个分组统一决定最终导入哪些配置类：

1234@Override
public Class<? extends Group> getImportGroup() {
    return AutoConfigurationGroup.class;
}

分好组后，Spring 会在每组中调用 DeferredImportSelectorGrouping#getImports() 方法。

对 AutoConfigurationGroup 这组，先来一个循环，依次保存候选配置类名和明确要求排除的类名，最后调用 group.selectImports() 汇总这些结果，得到最终要导入的配置信息：

1234567Iterable<Group.Entry> getImports() {
    for (DeferredImportSelectorHolder deferredImport : this.deferredImports) {
        this.group.process(deferredImport.getConfigurationClass().getMetadata(),
                deferredImport.getImportSelector());
    }
    return this.group.selectImports();
}

这里的 this.group 就是 AutoConfigurationGroup 实例。

循环里的 process() 方法接收两个参数：

  1. 第一个参数是发起导入的配置类上的 注解信息
  2. 第二个参数在本例是 AutoConfigurationImportSelector 实例

AutoConfigurationGroup#process() 把配置类上的注解信息传给 AutoConfigurationImportSelector#getAutoConfigurationEntry()，再把返回的 AutoConfigurationEntry 添加到 autoConfigurationEntries 中：

123AutoConfigurationEntry autoConfigurationEntry = autoConfigurationImportSelector
        .getAutoConfigurationEntry(annotationMetadata);
this.autoConfigurationEntries.add(autoConfigurationEntry);

通过 @SpringBootApplication 启动的应用里，annotationMetadata 就是主启动类的注解信息。

AutoConfigurationEntry 对象里包含两种信息：

  1. configurations：这一轮筛选后剩下的类名
  2. exclusions：保存明确排除的类名

深入看下 AutoConfigurationImportSelector#getAutoConfigurationEntry() 方法：

12345678910111213141516171819202122232425protected AutoConfigurationEntry getAutoConfigurationEntry(AnnotationMetadata annotationMetadata) {
    if (!isEnabled(annotationMetadata)) {
        return EMPTY_ENTRY;
    }
    AnnotationAttributes attributes = getAttributes(annotationMetadata);
    List<String> configurations = getCandidateConfigurations(annotationMetadata, attributes);
    configurations = removeDuplicates(configurations);
    Set<String> exclusions = getExclusions(annotationMetadata, attributes);
    checkExcludedClasses(configurations, exclusions);
    configurations.removeAll(exclusions);
    configurations = getConfigurationClassFilter().filter(configurations);
    fireAutoConfigurationImportEvents(configurations, exclusions);
    return new AutoConfigurationEntry(configurations, exclusions);
}

protected @Nullable AnnotationAttributes getAttributes(AnnotationMetadata metadata) {
    String name = getAnnotationClass().getName();
    AnnotationAttributes attributes = AnnotationAttributes.fromMap(metadata.getAnnotationAttributes(name, true));
    // --snip--
    return attributes;
}

protected Class<?> getAnnotationClass() {
    return EnableAutoConfiguration.class;
}

使用 getAttributes() 从主启动类的注解信息中读取 @EnableAutoConfiguration 注解的属性。

紧接着使用 getCandidateConfigurations() 方法获取候选配置类的全限定类名，其中就包含开头的例子里说的 HttpEncodingAutoConfiguration。

1.5 读取候选配置

getCandidateConfigurations() 方法内部调用了 ImportCandidates.load()：

123ImportCandidates importCandidates = ImportCandidates.load(this.autoConfigurationAnnotation,
        getBeanClassLoader());
List<String> configurations = importCandidates.getCandidates();

autoConfigurationAnnotation 默认为 AutoConfiguration.class。

深入 load() 方法，可以看到它默认从下面这个文件里读取候选配置类的全限定类名：

1META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

HttpEncodingAutoConfiguration 类位于 spring-boot-servlet 组件中。打开这个 JAR，在 .imports 文件里就包含它的全限定类名：

1org.springframework.boot.servlet.autoconfigure.HttpEncodingAutoConfiguration

如果多个 JAR 里有相同的 .imports 文件，Spring Boot 会依次读取并汇总它们内部包含的类名。

实际开发过程中通常不会直接引入 spring-boot-servlet 组件，而是引入 spring-boot-starter-webmvc。不过 spring-boot-starter-webmvc 会依赖 spring-boot-webmvc，后者依赖了 spring-boot-servlet，所以还是相当于引入了 spring-boot-servlet 组件。

load() 方法会使用类加载器的 getResources() 方法，按路径找出所有匹配的 .imports 文件，其中就包含 spring-boot-servlet 组件中的文件。

在低版本的 Spring Boot 中，自动配置信息放在 META-INF/spring.factories 的 EnableAutoConfiguration 键下。在 2.7 版本中引入 .imports 文件，并在 3.0 版本2中正式将自动配置信息的读取切换到 .imports 文件里，官方说这种方式更符合 Java SPI 的写法。不过 spring.factories 文件并不是就消失了，它还有别的用途。

1.6 筛选候选配置

再回到 AutoConfigurationImportSelector#getAutoConfigurationEntry() 方法里。

通过 getCandidateConfigurations() 方法已经获取到了所有的候选配置类的全限定类名，接下来还会进行去重、排除和过滤。

去重

同一个类名可能出现多次，调用的 removeDuplicates() 方法，使用 LinkedHashSet 保留第一次出现的位置。

排除

比如在启动类上写了 @SpringBootApplication(exclude = MultipartAutoConfiguration.class)，那么就应该从候选清单里移除 MultipartAutoConfiguration。

调用的 getExclusions() 方法从注解的 exclude、excludeName属性和配置 spring.autoconfigure.exclude 里收集到需要排除的候选信息，校验通过后，调用 configurations.removeAll(exclusions) 删掉这些项。

过滤

这一步对应调用的 getConfigurationClassFilter().filter(configurations) 方法。

第一次调用 getConfigurationClassFilter() 时，Spring Boot 先从 META-INF/spring.factories 加载 AutoConfigurationImportFilter 的实现。

在 spring-boot-autoconfigure 组件下，其 META-INF/spring.factories 文件中有这样一个配置：

12345# Auto Configuration Import Filters
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter=\
org.springframework.boot.autoconfigure.condition.OnBeanCondition,\
org.springframework.boot.autoconfigure.condition.OnClassCondition,\
org.springframework.boot.autoconfigure.condition.OnWebApplicationCondition

然后再用加载的 Filter 创建 ConfigurationClassFilter。构造对象时，会读取各组件的 META-INF/spring-autoconfigure-metadata.properties 文件里的配置信息，并保存到成员变量 autoConfigurationMetadata 中。

以 spring-boot-servlet 为例，这个文件里有这样一条记录：

1org.springframework.boot.servlet.autoconfigure.HttpEncodingAutoConfiguration.ConditionalOnClass=org.springframework.web.filter.CharacterEncodingFilter

等号左边是自动配置类和它的类条件，右边是它需要的类。

ConfigurationClassFilter#filter() 接收去重、排除后剩下的候选类名，把这份列表转成数组 candidates，再依次调用每个 AutoConfigurationImportFilter 的 match()：

  • 每次调用都传入整个数组和先前从 properties 文件中读到的配置信息
  • 返回的 match[i] 表示当前过滤器是否保留 candidates[i]。
123456789101112131415List<String> filter(List<String> configurations) {
    // --snip--
    @Nullable String[] candidates = StringUtils.toStringArray(configurations);
    boolean skipped = false;
    for (AutoConfigurationImportFilter filter : this.filters) {
        boolean[] match = filter.match(candidates, this.autoConfigurationMetadata);
        for (int i = 0; i < match.length; i++) {
            if (!match[i]) {
                candidates[i] = null;
                skipped = true;
            }
        }
    }
    // --snip--
}

以 HttpEncodingAutoConfiguration 为例：

  • 当 AutoConfigurationImportFilter 是 org.springframework.boot.autoconfigure.condition.OnClassCondition 时，它用 autoConfigurationMetadata.get(autoConfigurationClass, "ConditionalOnClass") 查找每个候选配置要求的类
  • HttpEncodingAutoConfiguration 被 @ConditionalOnClass(CharacterEncodingFilter.class) 注解标记，所以用它的类名加上 .ConditionalOnClass 作为 key，获取到 CharacterEncodingFilter 的全限定类名
  • 如果当前应用能成功加载 CharacterEncodingFilter 类，这一轮就保留 HttpEncodingAutoConfiguration；否则设置对应的 match[i] 为 false，之后外层循环会把 candidates[i] 设为 null，移除当前候选类名
  • 再回到上层 AutoConfigurationImportSelector#getAutoConfigurationEntry() 方法，执行完 filter() 方法后，最后再调用 fireAutoConfigurationImportEvents()，传入候选配置类名和明确需要移除的配置类名，触发事件监听，执行自动配置的后续逻辑（默认监听器会记录本次的候选配置类和排除项）

1.7 分组汇总与排序

回到先前讲的 getImports() 方法中，依次遍历 deferredImports 中的每个元素，取出配置类的注解信息和对应的 DeferredImportSelector 实例传给 group.process()。当前案例中的 group 是 org.springframework.boot.autoconfigure.AutoConfigurationImportSelector.AutoConfigurationGroup 实例，沿着它的 process() 方法，一直进入到 getAutoConfigurationEntry()。

现在 getAutoConfigurationEntry() 已经执行完，先把返回的 AutoConfigurationEntry 添加到 autoConfigurationEntries 中，然后又遍历这份结果中的候选类名，用 entries 记下每个类最早由哪个配置类导入。

1234for (String importClassName : autoConfigurationEntry.getConfigurations()) {
    // importClassName -> 候选类名，annotationMetadata -> 配置类的注解元数据
    this.entries.putIfAbsent(importClassName, annotationMetadata);
}

又回到 getImports()：

1234567Iterable<Group.Entry> getImports() {
    for (DeferredImportSelectorHolder deferredImport : this.deferredImports) {
       this.group.process(deferredImport.getConfigurationClass().getMetadata(),
             deferredImport.getImportSelector());
    }
    return this.group.selectImports();
}

所有 process() 方法都执行完成后，再调用 group.selectImports()。

在 AutoConfigurationGroup#selectImports() 中：

1234567891011public Iterable<Entry> selectImports() {
    if (this.autoConfigurationEntries.isEmpty()) {
       return Collections.emptyList();
    }
    Set<String> allExclusions = // --snip--
    Set<String> processedConfigurations = // --snip--
    processedConfigurations.removeAll(allExclusions);
    return sortAutoConfigurations(processedConfigurations, getAutoConfigurationMetadata()).stream()
       .map(this::getEntry)
       .toList();
}
  1. 先把明确要排除的类名赋值给 allExclusions
  2. 再把候选类名赋值给 processedConfigurations
  3. 然后再从候选名单里移除明确要排除的类名

先前在 getAutoConfigurationEntry() 里不是已经排除过一次吗，为什么这里又要再来一次呢？

假设一个配置类里排除了 MultipartAutoConfiguration，但另一个配置类的候选名单里还有它。如果不再整体做一次排除，那么它又「复活」了。

接下来调用 sortAutoConfigurations() 按自动配置类之间要求的顺序排序，最后返回 Group.Entry 列表。

例如在 @AutoConfiguration 的 after 属性里指定另一份配置类，这表示要在另一个配置类处理之后再处理当前配置类。

group.selectImports() 返回后，getImports() 把这批 Group.Entry 原样交还给调用方。

1.8 条件注册 Bean

回到最开始的例子，现在已经导入了 HttpEncodingAutoConfiguration 配置类，准备解析它。

它内部有一个 @Bean 方法：

12345@Bean
@ConditionalOnMissingBean
CharacterEncodingFilter characterEncodingFilter(ServletEncodingProperties properties) {
    // --snip--
}

该方法同时被 @ConditionalOnMissingBean 注解标记，且没有指定类型，因此 Spring Boot 默认按方法的返回类型 CharacterEncodingFilter 进行检查：

  • 如果容器里没有 CharacterEncodingFilter 类型的 Bean，那就使用当前 @Bean 方法注册默认的 Bean
  • 如果容器里已经有自定义的、CharacterEncodingFilter 类型的 Bean，那就用自定义的，不再注册默认的 Bean

关于配置类中 @Bean 方法的处理，可以参考 Spring 配置类的解析 一文，此处不再展开。

2. 再遇 OnClassCondition

HttpEncodingAutoConfiguration 类上也有许多形似 @ConditionalOnXxx 的注解：

12345678@AutoConfiguration
@EnableConfigurationProperties(ServletEncodingProperties.class)
@ConditionalOnWebApplication(type = Type.SERVLET)
@ConditionalOnClass(CharacterEncodingFilter.class)
@ConditionalOnBooleanProperty(name = "spring.servlet.encoding.enabled", matchIfMissing = true)
public final class HttpEncodingAutoConfiguration {
    // --snip--
}

@ConditionalOnClass(CharacterEncodingFilter.class) 要求应用能成功加载 CharacterEncodingFilter。

进入 @ConditionalOnClass，可以看到它用 @Conditional 指定了负责检查这个条件的类。

1234@Conditional(OnClassCondition.class)
public @interface ConditionalOnClass {
    // --snip--
}

又是 OnClassCondition。它在这里又有什么用呢？

前面讲到，Spring Boot 在筛选候选配置类类名时，如果应用中没有 CharacterEncodingFilter 类，就可以提前从候选名单里移除 HttpEncodingAutoConfiguration。

现在，当 Spring 解析 HttpEncodingAutoConfiguration 时，根据 @Conditional 调用 OnClassCondition 从父类 SpringBootCondition 继承的 matches() 方法。

具体的判断交给 OnClassCondition#getMatchOutcome() 方法完成：这里的 metadata 就是当前配置类的注解信息。

1234567891011121314151617public ConditionOutcome getMatchOutcome(ConditionContext context, AnnotatedTypeMetadata metadata) {
    ClassLoader classLoader = context.getClassLoader();
    // metadata -> 当前配置类的注解信息
    List<String> onClasses = getCandidates(metadata, ConditionalOnClass.class);
    if (onClasses != null) {
		// 判断目标类是否在应用中存在
        // 比如应用中不存在 CharacterEncodingFilter，那么 missing 就不为空
        List<String> missing = filter(onClasses, ClassNameFilter.MISSING, classLoader);
        if (!missing.isEmpty()) {
            return ConditionOutcome.noMatch(ConditionMessage.forCondition(ConditionalOnClass.class)
                                            .didNotFind("required class", "required classes")
                                            .items(Style.QUOTE, missing));
        }
        // --snip--
    }
    // --snip--
}

如果类加载器找不到它，missing 就不为空，Spring 会跳过这份配置。

不对啊，如果缺少 CharacterEncodingFilter类，在处理候选配置类时不就应该过滤掉了吗？

确实如此。这里相当于是一次兜底操作。在缺少 CharacterEncodingFilter 时，一开始就会过滤掉这个配置类。不过，只要配置类走到解析这一步，Spring 都会检查它上面的 @ConditionalOnClass。

3. 自定义自动配置

前面介绍了 Spring Boot 组件提供的自动配置，那如何在项目开发时自定义自动配置呢？

3.1 实现前的准备

声明一个 HelloWorldService，在构造它时需要传入一个 prefix：

1234567891011public class HelloWorldService {
    private final String prefix;

    public HelloWorldService(String prefix) {
        this.prefix = prefix;
    }

    public String sayHello(String name) {
        return this.prefix + name;
    }
}

假设 prefix 的默认值为 Hello, 。

为了方便更改，定义配置类 HelloWorldProperties，后续要修改默认值时，直接修改 demo.hello-world.prefix 配置即可：

123456@Setter
@Getter
@ConfigurationProperties("demo.hello-world")
public class HelloWorldProperties {
    private String prefix = "Hello, ";
}

仿照 HttpEncodingAutoConfiguration 的实现，写一个与 HelloWorldProperties 配套的自动配置类 HelloWorldAutoConfiguration：

1234567891011@AutoConfiguration
@ConditionalOnClass(HelloWorldService.class)
@ConditionalOnProperty(prefix = "demo.hello-world", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(HelloWorldProperties.class)
public class HelloWorldAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public HelloWorldService helloWorldService(HelloWorldProperties properties) {
        return new HelloWorldService(properties.getPrefix());
    }
}

HelloWorldAutoConfiguration 能被添加到 Spring 容器里的条件有两个：

  1. 当前应用能成功加载 HelloWorldService 类
  2. 没有 demo.hello-world.enabled 配置信息，或者其值为 true

HelloWorldAutoConfiguration 配置类内部还有一个 @Bean 方法 helloWorldService()，Spring 容器里不存在 HelloWorldService 类型的 Bean 时，使用这个 @Bean 方法创建一个默认的 HelloWorldService 类型的 Bean。

3.2 添加自动配置

把 HelloWorldAutoConfiguration 的全限定类名写入 src/test/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件中：

1indi.mofan.autoconfigure.helloworld.HelloWorldAutoConfiguration

当前只做测试，不需要其他项目（或模块）通过依赖当前模块使用这份配置，因此把这个 .imports 文件放在 src/test/ 目录下，而不是 src/main/ 目录下。

3.3 测试与验证

当前测试用不到 Web 环境，使用 ApplicationContextRunner 提供一个标准的 Spring 容器 Runner 就够了，然后通过 AutoConfigurations.of() 指定配置类：

123456789101112131415161718192021222324252627282930313233343536373839404142434445464748private final ApplicationContextRunner contextRunner = new ApplicationContextRunner()
        .withConfiguration(AutoConfigurations.of(HelloWorldAutoConfiguration.class));

@Test
public void testDefaultConfigurationCreatesHelloWorldService() {
    this.contextRunner.run(context -> {
        assertThat(context).hasSingleBean(HelloWorldService.class);
        assertThat(context.getBean(HelloWorldService.class)
                .sayHello("mofan"))
                .isEqualTo("Hello, mofan");
    });
}

@Test
public void testPrefixPropertyChangesHelloWorld() {
    this.contextRunner.withPropertyValues("demo.hello-world.prefix=你好，")
            .run(context ->
                    assertThat(context.getBean(HelloWorldService.class)
                            .sayHello("mofan"))
                            .isEqualTo("你好，mofan"));
}

@Test
public void testDisabledHelloWorldDoesNotCreateService() {
    this.contextRunner.withPropertyValues("demo.hello-world.enabled=false")
            .run(context -> {
                assertThat(context).doesNotHaveBean(HelloWorldAutoConfiguration.class);
                assertThat(context).doesNotHaveBean(HelloWorldService.class);
            });
}

@Test
public void testUserServiceMakesDefaultServiceBackOff() {
    this.contextRunner.withUserConfiguration(UserHelloWorldConfiguration.class).run(context -> {
        assertThat(context).hasSingleBean(HelloWorldService.class)
                .doesNotHaveBean("helloWorldService");
        assertThat(context.getBean(HelloWorldService.class))
                .isSameAs(context.getBean("customHelloWorldService"));
    });
}

@TestConfiguration(proxyBeanMethods = false)
static class UserHelloWorldConfiguration {
    @Bean
    HelloWorldService customHelloWorldService() {
        return new HelloWorldService("Hi, ");
    }
}

上述测试验证了四种情况：

  1. 默认情况下，容器提供默认的 HelloWorldService 类型的 Bean
  2. 通过修改配置，更改输出的前缀信息
  3. 通过修改配置，不加载 HelloWorldAutoConfiguration 配置类，容器里也没有 HelloWorldService
  4. 自定义 HelloWorldService 类型的 Bean，容器里不存在默认提供的且名为 helloWorldService 的 Bean

由于上面的测试使用 AutoConfigurations.of() 显式声明了自动配置 HelloWorldAutoConfiguration ，因此即使没有 .imports 文件，自动配置也会生效。

那怎么验证自动配置是由 .imports 文件登记的呢？

单独写一个只开启自动配置的入口：

1234@TestConfiguration(proxyBeanMethods = false)
@EnableAutoConfiguration
static class ImportApplication {
}

用一个新的 Runner，只传入 ImportApplication：

12345@Test
public void testEnableAutoConfigurationDiscoversImportsFile() {
    new ApplicationContextRunner().withUserConfiguration(ImportApplication.class)
            .run(context -> assertThat(context).hasSingleBean(HelloWorldService.class));
}

ImportApplication 中既没有扫描包，也没有显式导入 HelloWorldAutoConfiguration，但容器里有 HelloWorldService 类型的 Bean，说明 Spring Boot 通过 .imports 文件找到了配置类，并注册了它声明的 Bean。
