0. 前言

本文最初写于 2020-06-10，与 Spring Boot 自动配置原理 一样，是我初学 Spring Boot 时按教学视频记录的一份学习笔记。

Spring Boot 自动配置原理 偏向底层原理，这篇更偏向于实操。

我在翻新这篇文章时，对 Spring Boot 已经有了更深入的了解，难以再从初学者的角度出发，写出「Step by Step」的新手教程，因此文中可能涉及到一些源码解析的内容。对于初学者而言，这部分相对难以理解，建议直接跳过，只关注用法即可。

1. 使用 JdbcTemplate

1.1 数据库现状

现在 MySQL 里有一个 boot_study 库，库里有 tb_account 表，表结构如下：

1234567drop table if exists tb_account;
create table tb_account (
    id bigint primary key,
    account_name varchar(64) not null,
    balance decimal(12, 2) not null,
    updated_at timestamp not null default current_timestamp on update current_timestamp
) engine = InnoDB;

向这个表里添加两条数据：

123insert into tb_account(id, account_name, balance) values
    (1, 'Alice', 1000.00),
    (2, 'Bob', 500.00);

在 Spring Boot 项目里，如何连接数据库，并查询 Alice 账户下的余额呢？

1.2 查询前的准备

先在 pom.xml 里添加 JDBC Starter 和 MySQL 驱动：

123456789<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>

后续在集成测试里验证查询，因此还需要 spring-boot-starter-test：

12345<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>

在 src/main/resources/application.yaml 配置文件里添加数据库连接信息：

12345spring:
  datasource:
    url: jdbc:mysql://localhost:3306/boot_study
    username: root
    password: 123456

1.3 初识 JdbcTemplate

在 src/test/java 下创建测试类，包名和主启动类的包名保持一致，使得 @SpringBootTest 能正确找到启动类。

spring-jdbc 提供了 JdbcTemplate，使用它能够非常方便地查询数据库：

12345678910111213@SpringBootTest
@Sql({"/schema.sql", "/data.sql"})
class DatabaseIntegrationTest {
    @Autowired
    private JdbcTemplate jdbcTemplate;

    @Test
    void shouldSupportJdbcTemplateWithPositionalParameters() {
        BigDecimal balance = jdbcTemplate.queryForObject(
                "select balance from tb_account where id = ?", BigDecimal.class, 1L);
        assertThat(balance).isEqualByComparingTo("1000.00");
    }
}

每个测试方法执行前，@Sql 会先运行 schema.sql 建表，再运行 data.sql 插入 Alice 和 Bob 的记录，保证数据库内的数据一致。

运行测试方法时：

  • @SpringBootTest 会加载应用配置
  • @Autowired 把 Spring 创建的 JdbcTemplate 注入测试类

where id = ? 里的 ? 对应最后传入的参数 1L，即数据库里 Alice 账户的 id。

balance 列用 DECIMAL(12, 2) 存金额，传入 BigDecimal.class 按 BigDecimal 读取结果。

1.4 JdbcClient

刚刚只查了一列数据，如果要查一组数据，并用一个对象承载这些数据，可以怎么做呢？

用 Account 来承载数据：

12public record Account(long id, String accountName, BigDecimal balance, LocalDateTime updatedAt) {
}

定义 JdbcAccountDao，实现 findById()：

12345678910111213141516171819@Repository
public class JdbcAccountDao {
    private final JdbcClient jdbcClient;

    public JdbcAccountDao(JdbcClient jdbcClient) {
        this.jdbcClient = jdbcClient;
    }

    public Optional<Account> findById(long id) {
        return jdbcClient.sql("""
                        select id, account_name, balance, updated_at 
                        from tb_account 
                        where id = :id
                        """)
                .param("id", id)
                .query(Account.class)
                .optional();
    }
}

JdbcClient 是在 Spring 6.1 引入的接口，支持 JDBC 样式的位置参数和 Spring 样式的命名参数。

sql() 方法里的 id = :id 表示定义了一个命名参数 :id，并在查询时将其作为 id 列的值。

param("id", id) 表示把传入 findById() 方法的参数 id 绑定到 SQL 里的 :id。

query(Account.class) 则是把查到的结果映射成 Account 对象。

自动配置

之所以能直接在 DAO 里注入 JdbcClient，是因为 Spring Boot 自动配置了它：

12345678910@AutoConfiguration(after = JdbcTemplateAutoConfiguration.class)
@ConditionalOnSingleCandidate(NamedParameterJdbcTemplate.class)
@ConditionalOnMissingBean(JdbcClient.class)
@Import(DatabaseInitializationDependencyConfigurer.class)
public final class JdbcClientAutoConfiguration {
    @Bean
    JdbcClient jdbcClient(NamedParameterJdbcTemplate jdbcTemplate) {
        return JdbcClient.create(jdbcTemplate);
    }
}

@ConditionalOnSingleCandidate 注解的作用是：

  • Spring 容器里只有唯一一个指定类型的 Bean 时，相关配置才生效
  • 如果容器里有多个类型相同的 Bean，但有一个标记了 @Primary，配置也能生效

因此，在这里的含义是：

  • Spring 容器能唯一选定一个 NamedParameterJdbcTemplate 类型的 Bean 时，当前自动配置才生效

NamedParameterJdbcTemplate 由 JdbcTemplateAutoConfiguration 提供。

结果映射

Account 类中的字段名叫 accountName 和 updatedAt，数据库列名却叫 account_name 和 updated_at，Spring JDBC 支持在结果映射时，将下划线命名的数据库列名映射到小驼峰命名的 Java 字段上。

返回结果数量约定

在前面的例子里，如果去掉 where id = :id 条件，那么就是扫描 tb_account 全表，此时会查出 Alice 和 Bob 两条数据，再调用 optional() 方法就会抛出异常，因为这个方法要求最多只能返回一条数据。

如果要返回多条数据，可以使用 list() 方法。

与 optional() 类似的还有 single() 方法，它们之间的区别是对没有查询出结果的处理：

  • optional()：返回 Optional.empty()
  • single()：抛出 EmptyResultDataAccessException

2. 数据源与连接池

2.1 获取数据库连接

使用 JDBC 操作数据库的基本流程是：

  1. 引入 JDBC 驱动
  2. 获取数据库连接
  3. 准备 SQL 并绑定参数
  4. 执行 SQL 并处理结果
  5. 释放资源

上一节中，在 Maven 里引入了 JDBC 驱动，在配置文件里添加了连接数据库的必要信息，但后续使用时没有先获取数据库连接对象 java.sql.Connection，最后也没有释放资源。

那 JdbcTemplate 用的数据库连接是哪里来的？

前面提到的 JdbcTemplateAutoConfiguration 会导入 JdbcTemplateConfiguration，在这个配置类里，有个 @Bean 方法，就是通过这个方法创建了 JdbcTemplate：

12345678@Bean
@Primary
JdbcTemplate jdbcTemplate(DataSource dataSource, JdbcProperties properties,
		ObjectProvider<SQLExceptionTranslator> sqlExceptionTranslator) {
	JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);
	// --snip--
	return jdbcTemplate;
}

可以看到，在创建 JdbcTemplate 时，传入了 DataSource 对象。

DataSource 作为 @Bean 方法的参数，这表示将 Spring 容器里的 DataSource 类型的 Bean 作为参数传入这个方法。

那么问题又来了，容器里的 DataSource 又是怎么来的呢？

配置绑定

配置文件 application.yaml 中的数据库连接信息被绑定到 DataSourceProperties。

12345678@ConfigurationProperties("spring.datasource")
public class DataSourceProperties implements BeanClassLoaderAware, InitializingBean {
	private @Nullable String url;
	private @Nullable String username;
	private @Nullable String password;
	
	// --snip--
}

DataSourceProperties 则是由 DataSourceAutoConfiguration 通过 @EnableConfigurationProperties 注解将其注册到容器里：

1234@EnableConfigurationProperties(DataSourceProperties.class)
public final class DataSourceAutoConfiguration {
  // --snip--
}

创建数据源

配置信息已经进入 Spring 容器，那怎么根据这份信息创建数据源呢？

还是在 DataSourceAutoConfiguration 中，内部有个 PooledDataSourceConfiguration，它使用 @Import 注解导入了 DataSourceConfiguration.Hikari.class。

Hikari 是 DataSourceConfiguration 中嵌套的一个配置类：

12345678@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(HikariDataSource.class)
@ConditionalOnMissingBean(DataSource.class)
@ConditionalOnProperty(name = "spring.datasource.type", havingValue = "com.zaxxer.hikari.HikariDataSource",
		matchIfMissing = true)
static class Hikari {
  // --snip--
}

由于：

  • spring-boot-starter-jdbc 默认引入 HikariCP，所以应用能成功加载 HikariDataSource 类
  • 没有指定自定义数据源，容器里不存在 DataSource 类型的 Bean
  • 配置文件里没有指定数据源的类型

因此，Hikari 配置类的条件成立。

它里面有个名为 dataSource() 的 @Bean 方法：

12345678910@Bean
@ConfigurationProperties("spring.datasource.hikari")
HikariDataSource dataSource(DataSourceProperties properties, JdbcConnectionDetails connectionDetails,
       Environment environment) {
    // --snip--
    HikariDataSource dataSource = createDataSource(connectionDetails, HikariDataSource.class,
          properties.getClassLoader(), dataSourceClassName == null);
    // --snip--
    return dataSource;
}

HikariDataSource 实现了 javax.sql.DataSource，Spring Boot 默认情况下就是使用这个方法创建出 Hikari 数据源。

一点一点来。

先看 dataSource() 方法的参数，DataSourceProperties 和 Environment 在 Spring 容器里很好理解，那 JdbcConnectionDetails 又是怎么来的呢？

又回到 DataSourceAutoConfiguration 的内部类 PooledDataSourceConfiguration，刚刚看了它导入 Hikari，它里面还有个 @Bean 方法：

12345@Bean
@ConditionalOnMissingBean(JdbcConnectionDetails.class)
PropertiesJdbcConnectionDetails jdbcConnectionDetails(DataSourceProperties properties) {
    return new PropertiesJdbcConnectionDetails(properties);
}

默认情况下，容器里没有 JdbcConnectionDetails 类型的 Bean，条件成立，使用绑定了数据库连接信息的 DataSourceProperties 创建 PropertiesJdbcConnectionDetails 类型的 Bean，这个类型是 JdbcConnectionDetails 的实现类。

继续 dataSource() 方法，它内部调用了 createDataSource() 方法，通过 DataSourceBuilder 来创建数据源，关键是：

1234builder.url(connectionDetails.getJdbcUrl())
    .username(connectionDetails.getUsername())
    .password(connectionDetails.getPassword())
    .build();

到此，数据源就创建好了。

获取与释放连接

回到最开始的 JdbcTemplate#queryForObject()，简化调用链路，主要流程是：

1234JdbcTemplate.queryForObject()
  └─ JdbcTemplate.query()
      └─ JdbcTemplate.execute()
          └─ DataSourceUtils.getConnection()

使用 DataSourceUtils.getConnection() 方法，通过创建 JdbcTemplate 传入的 dataSource 对象，在执行查询语句前获取到数据库连接。

查询回调完成前，使用 JdbcUtils.closeResultSet() 关闭 ResultSet。

查询回调完成后，使用：

  • JdbcUtils.closeStatement() 清理 PreparedStatement
  • DataSourceUtils.releaseConnection() 释放连接

这一整套流程其实就是对 JDBC 的二次封装，让框架使用者只关心书写 SQL，不再关注业务之外的获取连接、释放连接的样板代码。

2.2 释放连接

介绍释放前，先看下是怎么获取到连接的。以未开启事务的查询为例，从上节说到的 DataSourceUtils.getConnection() 出发，大致调用流程是：

12345678DataSourceUtils.getConnection(dataSource)
  └─ DataSourceUtils.doGetConnection(dataSource)
      └─ DataSourceUtils.fetchConnection(dataSource)
          └─ HikariDataSource.getConnection()
              └─ HikariPool.getConnection()
                  └─ PoolEntry.createProxyConnection(...)
                      └─ ProxyFactory.getProxyConnection(...)
                          └─ new HikariProxyConnection(...)

如果在 IDE 里查看 ProxyFactory.getProxyConnection() 方法的源码，会发现它抛出了一个 IllegalStateException 异常，这是什么情况？那 HikariProxyConnection 对象是怎么创建的呢？

在这个方法体里有一句注释：

1// Body is replaced (injected) by JavassistProxyFactory

意思是，方法体会被 JavassistProxyFactory 替换。

先插播一个 Maven 相关的知识，一个 Maven 库可以同时提供主 JAR 和源 JAR。

以普通 Java 库为例，执行 mvn install 时，Maven 会在 compile 阶段将 .java 编译成 .class，在 package 阶段将 .class 和资源打进主 JAR，再在 install 阶段把主 JAR 和 POM 安装到本地 Maven 仓库，供其他项目依赖。默认的构建流程只会生成主 JAR。

如果配置了 Maven Source Plugin，在构建时打包 .java 文件并把源码 JAR 作为附加构建产物，那么执行 mvn install 时还会把 -sources.jar 也装进本地仓库。库作者发布这两个包后，使用者的 IDE 可以下载并关联源码包。点进依赖库中的类时，IDE 展示的是源码包里的 .java 文件。如果找不到对应版本的源码，IDE 才会反编译主 JAR 里的 .class 来展示。

HikariCP 应用了上述构建方式。在构建时，先在 compile 阶段编译带 throw 的 ProxyFactory.java，然后运行 JavassistProxyFactory 生成代理类并改写 ProxyFactory.class 中的 getProxyConnection() 方法。

所以，程序运行使用的是主 JAR HikariCP.jar 改写后的 .class，而在 IDE 里查看的源码 JAR HikariCP-sources.jar，那里面还是原来的 .java。

改写 getProxyConnection() 方法时会使用到 com.zaxxer.hikari.util.JavassistProxyFactory#modifyProxyFactory() 方法，它里面有一句：

123case "getProxyConnection":
    method.setBody("{return new " + packageName + ".HikariProxyConnection($$);}");
    break;

可以看到，获取到的连接对象是 HikariProxyConnection 对象。

简单来说，获取连接就是：

  • Hikari 从连接池中借出一个持有物理连接的 PoolEntry，再为这次借用创建 HikariProxyConnection，返回给调用方。

回到主线，看下释放连接做了些什么。从 DataSourceUtils.releaseConnection() 触发，大致调用流程是：

12345678DataSourceUtils.releaseConnection(con, dataSource)
  └─ DataSourceUtils.doReleaseConnection(...)
      └─ DataSourceUtils.doCloseConnection(...)
          └─ con.close()
              └─ ProxyConnection.close()
                  └─ PoolEntry.recycle()
                      └─ HikariPool.recycle()
                          └─ connectionBag.requite(poolEntry)

HikariProxyConnection 继承了 ProxyConnection，完整的释放逻辑在父类的 close() 方法里。

ProxyConnection#close() 在最后的 finally 语句里执行：

1234finally {
    delegate = ClosedConnection.CLOSED_CONNECTION;
    poolEntry.recycle();
}

delegate 原本保存底层物理连接，但这里并没有真正关闭连接，而是将它指向一个标记对象，表示当前借出的连接已经关闭，不能再用它执行 SQL，真实物理连接仍被 PoolEntry 持有。

再看 poolEntry.recycle()，它会调用 HikariPool#recycle()：

12345678910void recycle(final PoolEntry poolEntry)
{
   // --snip--
   if (poolEntry.isMarkedEvicted()) {
      closeConnection(poolEntry, EVICTED_CONNECTION_MESSAGE);
   } else {
      // --snip--
      connectionBag.requite(poolEntry);
   }
}

poolEntry.isMarkedEvicted() 判断通过时，Hikari 会真正地关闭物理连接。否则执行 requite() 归还连接，供后续请求使用。

所以，调用 Connection.close() 后并不意味着真的与 MySQL 断开连接。建立物理连接的开销巨大，使用连接池可以保留已经建立的连接，减少反复创建连接的开销。

不过，连接在用完之后仍要及时归还，否则当连接池里的连接都被占用时，后续请求就只能等待。

2.3 调整连接池配置

可以通过 spring.datasource.hikari 来调整 Hikari 连接池的配置，比如池的大小、空闲连接数、等待时间：

123456spring:
  datasource:
    hikari:
      maximum-pool-size: 4
      minimum-idle: 1
      connection-timeout: 1000
spring.datasource.hikari 下的配置示例值含义
maximum-pool-size4池中最多有 4 条连接，包括空闲和已借出的
minimum-idle1池尽量保留 1 条空闲连接，连接总数仍受上限约束
connection-timeout1000调用 getConnection() 等待可用连接的上限，单位为毫秒

如果 4 条连接都被使用，下次获取连接时就要等待。期间有连接归还，就可以继续使用，否则在超过配置的等待时间后抛出异常。

2.4 集成 Druid

添加适配了 Spring Boot 4 的 Druid 依赖：

12345<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid-spring-boot-4-starter</artifactId>
    <version>1.2.28</version>
</dependency>

在配置文件中使用 spring.datasource.druid 前缀对其进行配置：

1234567891011spring:
  datasource:
    druid:
      initial-size: 1
      min-idle: 1
      max-active: 4
      max-wait: 1000
      filter:
        stat:
          enabled: true
          slow-sql-millis: 500

其中：

  • initial-size 为初始连接数
  • min-idle 为最小空闲连接数
  • max-active 为最大连接数
  • max-wait 为获取连接的最大等待时间，单位为毫秒
  • stat 下的配置启用 Druid 自己的 StatFilter，并将慢 SQL 的判断阈值设为 500 毫秒

3. 事务管理器

一次业务调用往往涉及到多条 SQL 的执行。以转账为例，在入账失败时，应该撤销已经完成的扣款，这些操作必须放在同一个数据库事务里。

Spring 通过事务管理器控制事务。

在没有自定义 TransactionManager 类型的 Bean 的情况下，Spring Boot 会通过 DataSourceTransactionManagerAutoConfiguration 中的 JdbcTransactionManagerConfiguration 创建它。

这份配置要求容器中能够选定一个 DataSource，并且还没有 TransactionManager Bean。其 createTransactionManager() 方法根据配置选择具体实现：

123456789101112@Bean
@ConditionalOnMissingBean(TransactionManager.class)
DataSourceTransactionManager transactionManager(...) {
    DataSourceTransactionManager transactionManager = createTransactionManager(environment, dataSource);
    // --snip--
    return transactionManager;
}

private DataSourceTransactionManager createTransactionManager(Environment environment, DataSource dataSource) {
    return environment.getProperty("spring.dao.exceptiontranslation.enabled", Boolean.class, Boolean.TRUE)
          ? new JdbcTransactionManager(dataSource) : new DataSourceTransactionManager(dataSource);
}

默认情况下，spring.dao.exceptiontranslation.enabled 为 true，创建 JdbcTransactionManager 类型的 Bean，它继承了 DataSourceTransactionManager。

3.1 声明式事务管理

声明式事务管理由 @Transactional 注解实现。

Spring Boot 通过 TransactionAutoConfiguration 里的 EnableTransactionManagementConfiguration 启用注解事务管理：

123456789101112131415161718@Configuration(proxyBeanMethods = false)
@ConditionalOnBean(TransactionManager.class)
@ConditionalOnMissingBean(AbstractTransactionManagementConfiguration.class)
static class EnableTransactionManagementConfiguration {
    @Configuration(proxyBeanMethods = false)
    @EnableTransactionManagement(proxyTargetClass = false)
    @ConditionalOnBooleanProperty(name = "spring.aop.proxy-target-class", havingValue = false)
    static class JdkDynamicAutoProxyConfiguration {

    }

    @Configuration(proxyBeanMethods = false)
    @EnableTransactionManagement(proxyTargetClass = true)
    @ConditionalOnBooleanProperty(name = "spring.aop.proxy-target-class", matchIfMissing = true)
    static class CglibAutoProxyConfiguration {

    }
}

容器里已经有 TransactionManager 类型的 Bean，并且没有 AbstractTransactionManagementConfiguration 类型的 Bean（没有自行启用注解事务管理）时，EnableTransactionManagementConfiguration 生效。

内部有两个类 JdkDynamicAutoProxyConfiguration 和 CglibAutoProxyConfiguration，它们区别不大，都会启用以 @Transactional 实现的声明式事务管理。

区别在 @EnableTransactionManagement 注解的 proxyTargetClass 属性上，这个属性控制的是创建代理的方式，是 JDK 的动态代理，还是 CGLib 动态代理。

至于 @EnableTransactionManagement 是如何启用声明式事务管理，以及 @Transactional 是如何工作的，这里不再展开。

3.2 编程式事务管理

使用 TransactionTemplate 实现编程式事务，它也是在 TransactionAutoConfiguration 配置类里创建：

123456789@Configuration(proxyBeanMethods = false)
@ConditionalOnSingleCandidate(PlatformTransactionManager.class)
static class TransactionTemplateConfiguration {
    @Bean
    @ConditionalOnMissingBean(TransactionOperations.class)
    TransactionTemplate transactionTemplate(PlatformTransactionManager transactionManager) {
        return new TransactionTemplate(transactionManager);
    }
}

容器中能够选定一个 PlatformTransactionManager，且还没有 TransactionOperations 类型（TransactionTemplate 实现了 TransactionOperations）的 Bean 时，Spring Boot 就会基于这个事务管理器创建 TransactionTemplate。

4. 集成 MyBatis

4.1 自动配置 MyBatis

引入依赖：

12345<dependency>
    <groupId>org.mybatis.spring.boot</groupId>
    <artifactId>mybatis-spring-boot-starter</artifactId>
    <version>${mybatis.version}</version>
</dependency>

MyBatis 的自动配置由 MybatisAutoConfiguration 完成，该类上的条件和绑定的配置有：

123@ConditionalOnClass({ SqlSessionFactory.class, SqlSessionFactoryBean.class })
@ConditionalOnSingleCandidate(DataSource.class)
@EnableConfigurationProperties(MybatisProperties.class)

它内部还有一个名为 sqlSessionFactory() 的 @Bean 方法：

12345@Bean
@ConditionalOnMissingBean
public SqlSessionFactory sqlSessionFactory(DataSource dataSource) throws Exception {
  // --snip--
}

使用容器里已经存在的 DataSource 创建 SqlSessionFactory 类型的 Bean，因此既不需要手动创建 SqlSessionFactory，也不需要再额外配置一套数据库连接信息。

4.2 Mapper 扫描与配置

引入 MyBatis 的 Starter 后，在没有自定义 Mapper 扫描配置时，会扫描主启动类所在包及其子包里带有 @Mapper 注解的接口，并注册 Mapper 代理，后续就可以在业务类里注入 Mapper 接口。

如果 Mapper 放在了其他包，可以使用 mybatis-spring 提供的 @MapperScan 注解指定扫描范围。

Mapper 接口能被扫描到了，还要在配置文件里指定 SQL 映射文件的存放位置：

12mybatis:
  mapper-locations: classpath:/mapper/*.xml
